# Ping Monitor

Internet latency as a live graph on the BUSY Bar.

The bar keeps measuring the round trip to a host of your choice, twice a second by default (the period is a setting), and draws it across the whole screen: one column per measurement, newest on the right. The latest value sits in the top-left corner. Columns are green while latency is low, yellow from 60 ms and red from 150 ms by default; a lost probe is a dotted red column.

On start the app shows the host it connects to, with a packet running along a link until the first answer arrives. Then the link flashes green (red without an answer) and the graph wipes in.

## Controls

| Control | Action |
| --- | --- |
| Wheel | Changes the vertical scale step by step: 100, 200, 500 ms, 1, 2 s at the top of the graph. The new scale shows in the top-right corner for a moment. Until the first turn the scale is automatic. |
| Start | Clears the graph. |
| Back | Quits the app. |

## Vertical scale

The bottom of the graph is 0 ms. With the automatic scale, the top follows the highest value on screen, rounded up a little, between 100 ms and 2 s. Anything slower than the top shows as a full-height column. One spike flattens the rest of the graph until it scrolls off the left edge, 36 seconds later at the default period. Turn the wheel to fix the scale instead.

## Settings

| Setting | Default | Description |
| --- | --- | --- |
| Host | `1.1.1.1` | An IP address, a host name, or a full `http://` address. |
| Update period, ms | `500` | How often to measure, 200 to 60000. |
| Value font | Small | Font of the latency number: Tiny, Small (5 px), Condensed, Normal or Bold (7 px). |
| Yellow from, ms | `60` | Latency from which columns turn yellow. |
| Red from, ms | `150` | Latency from which columns turn red. |

## How it measures

Apps on the BUSY Bar can't send ICMP pings, so the app times one small plain-HTTP request to the host instead. The numbers come out a bit higher than `ping` shows, because a request also needs a TCP handshake. The host must answer plain HTTP on port 80: `1.1.1.1`, `208.67.222.222` and `google.com` do, `8.8.8.8` and `9.9.9.9` don't. A request that gets no answer within 1.5 s (or two periods, if that is longer, up to 3 s) counts as lost.

## Development

```sh
npm install
npm run typecheck
npm run build         # dist/io.github.rnadyrshin.pingmonitor.tgz
npm run app:install   # install it on the BUSY Bar connected over USB
```

`dev/deploy.sh` installs and launches the built package with `curl` only. `dev/screen.py` prints the bar's front screen as text and saves a PNG.

The intro animation `src/animations/link.anim` is generated by `dev/tools/make_anim.py`. It downloads the converter `seq2anim.py` from the BUSY Bar firmware repository on the first run and needs Python 3.10+ with Pillow:

```sh
python3 -m venv dev/tools/.venv && dev/tools/.venv/bin/pip install pillow
dev/tools/.venv/bin/python dev/tools/make_anim.py
```

## Releases

Pushing a tag that matches `version` in `src/appmeta/manifest.json`, e.g. `1.0.0` without a `v`, builds the app and attaches `io.github.rnadyrshin.pingmonitor-<version>.tgz` to a GitHub release (`.github/workflows/release.yml`). Download the `.tgz` from the release to install a version by hand.
